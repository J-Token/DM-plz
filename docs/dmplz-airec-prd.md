## 1. 제품 요약

DM-Plz는 Claude Code가 사용자 입력이 필요하거나 진행 상황을 보고할 때 Telegram/Discord로 메시지를 보내는 플러그인이다. 폰만 들고 있어도 원격에서 승인·거부하고 다음 지시를 내릴 수 있다. 즉 **원격 조종 루프는 이미 완성돼 있다.**

빠진 것은 **확인 루프**다. 사용자가 폰에서 받는 것은 Claude가 스스로 요약한 텍스트뿐이다. "설치 마법사를 끝까지 진행했습니다"를 검증하려면 PC 앞으로 돌아가야 한다. 텍스트 요약은 에이전트가 자기 작업을 자기가 평가한 결과이므로 증거가 아니라 주장이다.

airec는 이 문제를 정확히 겨냥한 윈도우 CLI다. WGC로 가려진 창도 녹화하고, 클릭·드래그를 프레임에 합성하며, JSONL과 `stop_reason`으로 "이 증거를 믿어도 되는지"를 기계적으로 판정하게 해준다. 업로드는 의도적으로 없다.

그런데 이 두 개를 붙일 때 **어디에 코드를 놓을지**가 더 중요한 판단이다. DM-Plz의 사용자 대다수는 airec를 쓰지 않고, 상당수는 윈도우도 아니다. 이들에게 녹화 세션 레지스트리, 파일 락, GIF 폴백 체인, 보존 정책 코드를 떠안기는 것은 대가가 있다. 코어가 커지면 기동이 느려지고 회귀 위험이 늘고 설정 표면이 넓어진다.

> 코어에는 airec를 전혀 모르는 사용자에게도 쓸모 있는 것만 넣는다. 나머지는 전부 떼어낼 수 있는 스킬에 둔다.

이 기준을 적용하면 코어에 남는 것은 **"로컬 파일 하나를 첨부해서 보낸다"** 뿐이다. 이건 스크린샷, 로그, 빌드 산출물, 리포트 PDF에도 쓰이는 메신저 클라이언트의 당연한 능력이고, airec 없이도 그 자체로 유용하다. 반면 언제 녹화할지, 대상 창을 어떻게 고를지, 용량이 넘치면 어떻게 줄일지, `stop_reason`을 어떻게 읽을지는 전부 판단이며 — 그 판단은 지금의 모델이 문서만 있으면 해낸다.

그래서 이 PRD의 결과물은 서버 모듈이 아니라 **스킬 하나와 provider 메서드 하나**다. 사용자가 원하지 않으면 스킬은 설치되지 않고, 설치했다가 마음이 바뀌면 한 줄로 지운다. 코어는 어느 쪽이든 모른다.

## 2. 배경과 문제 정의

### 2.1 현재 DM-Plz의 한계

| 접점 | 사용자가 받는 것 | 한계 |
| --- | --- | --- |
| `Stop` 훅 | transcript에서 추출한 작업 요약 | 도구 이름과 파일명 나열. GUI 조작은 흔적이 거의 없다 |
| `PermissionRequest` 훅 | 승인 대상 도구/명령 문자열 | 지금 화면 상태를 알 수 없다 |
| `AskUserQuestion` 훅 | 질문 텍스트와 선택지 | 판단에 필요한 시각 맥락이 없다 |
| MCP 도구 4종 | Claude가 작성한 텍스트 | 자기 보고 |

공통점이 하나 있다. **DM-Plz는 지금까지 텍스트만 보낼 수 있다.** 파일을 보낼 능력 자체가 없다.

### 2.2 대안이 부족한 이유

**스크린샷**: 순간만 보여준다. 마법사 5단계 중 마지막 화면만으로는 중간 오조작을 알 수 없다.

**transcript 요약 강화**: 품질을 올려도 자기 보고라는 성질은 안 바뀐다. 에이전트가 실패를 성공으로 오인하면 요약도 같이 틀린다.

**ffmpeg/OBS 직접 연동**: 설치 부담, 창 지정 어려움, 가려지면 다른 창이 찍힘. 무엇보다 정상 종료 여부를 스크립트가 판정할 구조화 출력이 없다.

**airec에 업로드 기능 추가**: airec는 네트워크를 건드리지 않는 것을 원칙으로 명시했다. 그 원칙을 깨는 대신 네트워크를 이미 담당하는 쪽이 가져간다.

**DM-Plz 코어에 녹화 전체를 통합**: 이 PRD의 v0.2안이었고, 폐기했다. 이유는 §3.3.

### 2.3 왜 지금인가

- airec v0.2.x는 에이전트가 쓰기 위한 계약(세션 분리, JSONL, `stop_reason`, 에러 코드, GIF 변환)을 이미 전부 제공한다. **v0.1은 airec 코드 변경 없이 성립해야 한다.**
- 모델 성능이 올라, "언제 녹화하고 어떻게 판정할지"를 코드 대신 문서로 지시해도 동작한다. 3년 전이면 훅과 상태 머신이 필요했을 일이다.

## 3. 제품 목표

### 3.1 핵심 목표

1. Claude가 수행한 GUI 작업을 **MP4/GIF 증거로 메신저에 첨부**해 사용자가 폰에서 재생할 수 있게 한다.
2. 증거의 **신뢰 여부를 사용자가 한 줄로 판정**할 수 있게 한다.
3. 이 기능 전체가 **설치되지 않을 수 있어야 하고**, 설치되지 않았을 때 DM-Plz는 지금과 100 % 동일해야 한다.
4. 화면 녹화의 민감성을 고려해 **명시적 opt-in**으로만 동작한다.

### 3.2 제품 철학

- DM-Plz는 운반자다. 캡처·인코딩·판정은 airec의 일이다.
- **있으면 더 좋고, 없으면 그만이다.** 이 기능은 코어의 전제가 되어서는 안 된다.
- 판단은 모델에게, 대기는 훅에게, 운반은 코어에게.
- 에이전트가 "성공했다"고 말하는 것과 사용자가 "성공을 봤다"는 것은 다르다. 후자를 만든다.
- 화면은 비밀을 담는다. 기본값은 항상 "보내지 않음"이다.

### 3.3 모듈 경계 판정 기준

무엇을 코어에 넣고 무엇을 스킬로 뺄지는 하나의 질문으로 결정한다.

> **airec를 전혀 모르는 사용자에게도 쓸모 있는가?**

| 후보 | 판정 | 위치 |
| --- | --- | --- |
| 로컬 파일 첨부 전송 | 예 — 스크린샷, 로그, 빌드 산출물, PDF에 쓰인다 | **코어** |
| provider별 업로드 상한 판정 | 예 — 어떤 파일이든 필요하다 | **코어** |
| airec 설치 탐지 | 아니오 | 스킬 |
| 녹화 세션 시작/종료/추적 | 아니오 | 스킬 (airec가 이미 세션을 관리한다) |
| `stop_reason` 신뢰도 판정 | 아니오 | 스킬 |
| GIF 변환 폴백 체인 | 아니오 | 스킬 |
| 녹화 아티팩트 보존 정책 | 아니오 | 스킬 (또는 `airec.toml`) |
| "지금 녹화해야 하나" 판단 | 아니오 | 스킬 |

v0.2안에서 계획했던 `server/src/recorder/*`(4파일)과 `server/src/media/*`(2파일)는 **전부 사라진다.** 코어 변경은 `types.ts` 인터페이스 1줄, provider 2개의 메서드 구현, MCP 도구 1개 등록이 전부다.

## 4. 비목표

v0.x 전체에서 하지 않는 것:

- **코어에 녹화 로직을 넣는 것.** 세션 레지스트리, 파일 락, 폴백 체인, 보존 스케줄러를 서버에 만들지 않는다.
- **신규 훅 추가.** 훅은 무한 대기 전용으로 현행 3종을 유지한다(§9).
- **녹화 엔진 자체 구현.** 캡처·인코딩·커서 합성·GIF 변환은 전부 airec에 위임한다.
- **airec 자동 설치.** DM-Plz가 실행 파일을 내려받지 않는다. 안내만 한다.
- **클라우드 업로드/호스팅.** 파일은 Telegram/Discord 첨부로만 나간다.
- **영상 편집·트리밍·구간 선택.**
- **오디오 녹음, 키보드 입력 기록.**
- **영상 내용의 LLM 자동 분석/요약.** 증거는 사람이 본다.
- **실시간 스트리밍/미러링.**
- **자동 마스킹/블러.** 오탐이 곧 유출이다.
- **스킬을 코어 플러그인에 강제 번들.** 설치는 사용자가 별도로 지시해야 한다(§7.3).

## 5. 타깃 사용자

**1차 — 원격에서 Claude Code를 굴리는 개인 개발자**
- 데스크톱에 Claude Code를 띄워두고 외출한 뒤 폰으로 지시를 잇는 사람. 현행 DM-Plz의 핵심 사용자.
- 원하는 것: "다 했다"는 말 대신 "이렇게 했다"는 화면.

**2차 — 에이전트에게 GUI 작업을 맡기는 사용자**
- computer-use, Playwright, 데스크톱 자동화로 UI 조작을 시키는 사람.
- 원하는 것: 실패 시 어느 단계에서 어긋났는지 볼 수 있는 기록.

**3차 — Discord 채널로 작업을 공유하는 소규모 팀**
- 원하는 것: PR에 붙일 GIF, 리뷰어가 재현 없이 보는 결과물.

**0차(중요) — 이 기능을 쓰지 않는 기존 사용자**
- macOS 사용자, 텍스트 알림만 쓰는 사용자.
- 원하는 것: **아무것도 달라지지 않는 것.** 이들이 이 PRD의 제약 조건이다.

## 6. 핵심 사용 시나리오

### 시나리오 1: 모듈 없이 파일만 보내기 (코어 기능)

Claude가 벤치마크 결과 차트를 그렸다. 사용자는 폰에서 그림을 보고 싶다.

```ts
send_media({ file_path: "C:\\work\\bench.png", caption: "p95 레이턴시 비교" })
```

요구사항:
- airec 설치 여부와 무관하게 동작한다.
- 상한 초과 시 무엇이 문제인지(크기, 상한) 구조화 값으로 알려준다.

성공 기준:
- 스킬을 설치하지 않은 사용자도 이 도구를 쓸 수 있다.

---

### 시나리오 2: 사용자가 증거 모듈을 설치

사용자가 "GUI 작업할 때 녹화해서 보내주면 좋겠는데"라고 말한다.

```powershell
irm https://raw.githubusercontent.com/j-token/airec/main/install.ps1 | iex
npx skills add j-token/dm-plz --skill dm-plz-evidence
```

요구사항:
- 두 줄이 전부다. 코어 재설치, 플러그인 재시작, 설정 파일 편집이 필요 없다.
- 스킬 문서가 CLI 설치 방법도 함께 안내한다.

성공 기준:
- 설치 후 별도 설정 없이 다음 GUI 작업부터 동작한다.
- `npx skills remove`로 지우면 코어는 영향받지 않는다.

---

### 시나리오 3: GUI 작업 증거 전송

폰에서 "설치 마법사 끝까지 진행해줘"라고 지시했다.

```powershell
# 스킬 지시에 따라 모델이 직접 실행
airec start --window "Setup" --out C:\...\installer.mp4 --max-duration 30m --json
# {"event":"started","session":"a1b2"}
```
```
(computer-use로 마법사 진행)
```
```powershell
airec stop --session a1b2 --json
# {"event":"saved","file":"...","stop_reason":"requested","duration_ms":12400,...}
```
```ts
send_media({ file_path: "C:\\...\\installer.mp4",
             caption: "설치 마법사 5단계 완료\n\n🎬 12.4초 · 3.1 MB\n✅ 정상 종료" })
```

요구사항:
- 세션 ID 추적, `stop_reason` 판정, 캡션 조립은 모델이 스킬 규칙대로 수행한다.
- 코어는 파일 경로와 캡션만 받는다.

성공 기준:
- 폰에서 마우스 클릭 효과가 보이는 영상을 재생할 수 있다.
- `target_lost`로 끝났다면 캡션 첫 줄에 경고가 붙는다.

---

### 시나리오 4: 용량 초과

40분 작업이 200 MB MP4로 나왔다. `send_media`가 상한 초과를 알린다.

```ts
send_media({ file_path: "...long.mp4" })
// → { error: { code: "MEDIA_TOO_LARGE", data: { sizeBytes: 209715200, limitBytes: 52428800 } } }
```
```powershell
airec convert ...long.mp4 --out ...long.gif --fps 10 --width 960 --json
```
```ts
send_media({ file_path: "...long.gif" })   // 재시도
```

요구사항:
- 코어는 재시도 루프를 만들지 않는다. 무엇이 왜 실패했는지만 정확히 반환한다.
- 스킬은 축소 시도 횟수 상한(2회)과 포기 조건을 규정한다.

성공 기준:
- 최종 실패해도 사용자는 로컬 경로와 크기를 안내받는다. 침묵하지 않는다.

---

### 시나리오 5: 모듈 미설치 / 비윈도우

macOS 사용자가 DM-Plz만 쓴다.

요구사항:
- 녹화 관련 코드 경로가 애초에 존재하지 않는다(코어에 없으므로).
- `send_media`는 정상 노출되고 동작한다.

성공 기준:
- 기존 4개 도구, 3개 훅의 동작이 100 % 동일하다.
- 사용자는 이 기능의 존재조차 모를 수 있다.

## 7. 제품 범위

### 7.1 레이어 구조

세 레이어는 각각 독립적으로 설치·제거된다.

| 레이어 | 산출물 | 설치 방법 | 없으면 |
| --- | --- | --- | --- |
| **L1 코어** | `send_media` MCP 도구 + `sendMedia()` provider 메서드 | 기존 플러그인 업데이트 | 파일 첨부 불가(현행과 동일) |
| **L2 모듈** | `dm-plz-evidence` 스킬 문서 | `npx skills add` | 모델이 녹화 판단을 안 함. 사용자가 직접 지시하면 여전히 가능 |
| **L3 레코더** | `airec.exe` | `install.ps1` | 녹화 자체 불가. L1은 정상 |

### 7.2 v0.1 범위

**L1 코어 (필수, 코어 저장소)**

### 7.3 스킬을 번들하지 않는 이유

플러그인에 스킬을 넣으면 설치가 한 번에 끝난다. 그럼에도 넣지 않는다.

- 번들된 스킬은 사용자가 원하지 않아도 스킬 목록에 뜬다. "있으면 더 좋고 없으면 그만"이 아니라 "항상 있음"이 된다.
- 스킬 `description`은 모델이 매 요청에서 훑는 대상이다. 안 쓸 기능의 설명이 상주하는 것은 비용이다.
- 코어 릴리즈와 모듈 릴리즈가 묶이면, 녹화 규칙 한 줄 고치는 데 플러그인 버전을 올려야 한다.
- 제거가 비대칭이 된다. 설치는 한 줄인데 제거는 플러그인 설정을 건드려야 한다면 모듈이 아니다.

대신 발견 가능성은 문서로 확보한다. README에 "증거 녹화까지 원하면 이 두 줄"을 명시하고, `send_media` 도구 설명 끝에 한 문장으로 안내한다.

#### 미해결 문제

- **문제**: 스킬을 `dm-plz` 저장소에 둘지, `airec` 저장소에 둘지, 별도 저장소로 뺄지
- **영향**: `airec` 쪽에 두면 airec 사용자가 먼저 발견하고, `dm-plz` 쪽에 두면 원격 알림 사용자가 먼저 발견한다. 스킬 내용은 양쪽 지식을 다 요구한다
- **후보**: `dm-plz/skills/` (권장 — 전송이 주된 목적) / `airec/skills/` / 별도
- **결정 필요 시점**: v0.1 릴리즈 전

### 7.4 v0.2 범위

- `Stop` 훅 안전망 첨부: 활성 airec 세션이 남아 있을 때만 종료 후 첨부(예산 60초). **훅 코드에 조건부 분기 하나만 추가하며, 세션 탐색은 `airec status --json` 한 번으로 끝낸다.**

## 8. 기능 요구사항

FR 번호는 레이어로 나눈다. **0번대는 코어, 100번대는 모듈이다.** 100번대는 코드가 아니라 스킬 문서에 서술되는 규칙이며, 수용 기준은 "모델이 그렇게 행동하는가"로 검증한다.

### FR-001: 미디어 전송 인터페이스 (L1)

`MessagingProvider`는 로컬 파일을 첨부로 전송할 수 있어야 한다.

요구사항:
- 인터페이스에 다음을 추가한다.

```ts
sendMedia(
  filePath: string,
  options?: {
    caption?: string
    parseMode?: 'Markdown' | 'HTML'
    kind?: 'video' | 'animation' | 'document' | 'photo'
    route?: 'default' | 'permission'   // 목적지가 아니라 라우팅 종류
  }
): Promise<{ messageId: string }>
```

- **목적지는 설정에서만 온다.** 호출자가 임의의 chat/channel ID를 지정할 수 없다. `route`는 기존 라우팅 규칙 중 하나를 고르는 열거형이며, 실제 ID 해석은 provider 내부에서 환경변수로 이뤄진다(§13.1).
- `kind` 생략 시 확장자와 파일 크기로 자동 결정한다.
- 업로드 상한은 provider 구현이 알고 있으며, 호출자는 `MEDIA_TOO_LARGE`로만 판단한다.
- 전송량은 상한 검사를 통과한 시점의 크기로 고정한다. 검사 이후 파일이 커져도 그 바이트는 나가지 않는다.
- 파일 미존재, 읽기 불가, 크기 0은 전송 시도 전에 구조화 에러로 반환한다.

수용 기준:
- provider 두 구현체가 모두 `sendMedia`를 구현하며 타입 체크가 통과한다.
- 캡션이 플랫폼 상한(Telegram 1024자)을 넘으면 잘라내고 말줄임을 붙인다.
- 전송 실패 시 예외가 아니라 구조화 에러로 반환된다.
- 상한 초과 파일에 대해 네트워크 요청이 발생하지 않는다.
- 검사 통과 후 파일이 커져도 검사 시점 크기만 전송된다.
- 업로드 중 프로세스 RSS 증가가 파일 크기의 3배를 넘지 않으며, 업로드 종료 후 해제된다(§10.4).

### FR-002: Telegram 미디어 전송 (L1)

요구사항:
- 30초 이하 MP4는 `sendAnimation`으로 보낸다. airec 출력은 오디오 없는 H.264 yuv420p이므로 Telegram에서 자동 루프 재생되며, 짧은 증거 영상에 가장 적합하다.
- 30초 초과 MP4는 `sendVideo`로 보낸다.
- GIF는 `sendAnimation`, 이미지는 `sendPhoto`, 그 외는 `sendDocument`로 보낸다.
- `multipart/form-data`로 업로드한다.
- 상한 50 MB로 간주하고, 초과 시 요청을 보내지 않고 `MEDIA_TOO_LARGE`를 반환한다.
- 기존 채팅 라우팅 규칙(`DMPLZ_PERMISSION_CHAT_ID` → 기본 채팅)을 승계한다.

수용 기준:
- 12초 MP4가 Telegram에서 인라인 재생된다.
- 캡션 Markdown이 정상 렌더링된다.
- 60 MB 파일에서 네트워크 요청 없이 즉시 `MEDIA_TOO_LARGE`와 `limitBytes`가 반환된다.

#### 미해결 문제

- **문제**: airec의 fragmented MP4가 Telegram 서버 트랜스코딩/썸네일 생성과 호환되는지 미검증
- **영향**: 비호환 시 `sendDocument` 폴백이 필요하고 인라인 재생 UX가 나빠진다
- **후보**: 실측 후 결정 / `sendDocument` 고정
- **결정 필요 시점**: v0.1 구현 중(실측 필수)

### FR-003: Discord 미디어 전송 (L1)

요구사항:
- `POST /channels/{id}/messages`에 `multipart/form-data`로 `payload_json` + `files[0]`을 보낸다.
- 상한 기본값 10 MiB, `DMPLZ_MEDIA_MAX_BYTES`로 조정 가능하다.
- DM 경로(`DMPLZ_DISCORD_DM_USER_ID`)에서도 동일하게 동작한다.
- 429 응답 시 `retry_after`만큼 대기 후 1회 재시도한다.

수용 기준:
- 채널과 DM 양쪽에서 MP4 첨부가 재생 가능한 형태로 표시된다.
- 상한 초과 시 요청 없이 `MEDIA_TOO_LARGE`를 반환한다.
- 429 재시도 1회 후에도 실패하면 구조화 에러를 반환한다.

#### 미해결 문제

- **문제**: Discord 기본 첨부 상한은 부스트 레벨에 따라 다르고 정책 변경 이력이 있다
- **영향**: 낙관적으로 잡으면 매번 실패 후 재시도하는 낭비가 생긴다
- **후보**: 보수적 10 MiB + 환경변수 조정 / 길드 조회 자동 판정(v0.3)
- **결정 필요 시점**: v0.1 구현 전

### FR-004: MCP 도구 `send_media` (L1)

요구사항:
- 입력: `file_path`(필수, 절대 경로), `caption`(선택), `kind`(선택).
- **목적지 파라미터를 받지 않는다.** 도구 스키마에 chat/channel ID가 존재하지 않는다(§13.1).
- 출력: `sent`, `message_id`, 또는 구조화 에러.
- 도구 설명은 짧게 유지한다. 증거 녹화 관련 지시는 넣지 않고, 마지막에 모듈 존재만 한 문장으로 안내한다.
- `DMPLZ_MEDIA_ENABLED=false`면 도구를 목록에 노출하지 않는다(기본값은 `true`).
- 상대 경로는 거부한다. 작업 디렉터리 기준 해석의 모호함을 만들지 않는다.
- **파일 내용에 대한 필터(확장자 allowlist 등)를 두지 않는다.** 근거는 §13.2.

수용 기준:
- 스킬 미설치 상태에서도 사용자가 명시 요청하면 파일이 전송된다.
- 존재하지 않는 경로에 대해 `FILE_NOT_FOUND`가 반환되고 예외로 죽지 않는다.
- 도구 설명이 300자를 넘지 않는다.
- 도구 입력 스키마에 목적지를 지정하는 필드가 없다.

### FR-005: 코어 실패 격리 (L1)

요구사항:
- 미디어 전송 실패는 기존 텍스트 전송 경로에 영향을 주지 않는다.
- 업로드에 타임아웃을 건다(기본 120초, `DMPLZ_MEDIA_TIMEOUT_MS`).
- 훅 경로에서 미디어 관련 예외가 발생해도 exit code를 바꾸지 않는다.

수용 기준:
- 네트워크 차단 상태에서 `send_media` 호출이 타임아웃 후 구조화 에러로 복귀한다.
- 미디어 전송 중에도 MCP 도구 목록 조회가 정상 응답한다.

### FR-101: 모듈 패키징과 독립 설치 (L2)

`dm-plz-evidence`는 코어와 독립적으로 설치·제거되어야 한다.

요구사항:
- 스킬은 단일 `SKILL.md`로 구성한다. 실행 코드, 스크립트, 의존성을 포함하지 않는다.
- `description`에 트리거 조건을 명시한다: "GUI·데스크톱 조작 결과를 원격 사용자에게 화면 증거로 증명해야 할 때".
- 스킬 본문 첫 절은 전제 조건 확인이다: `send_media` 도구 존재 여부, `airec --version` 성공 여부.
- 설치·제거 명령을 스킬 문서와 README 양쪽에 적는다.

수용 기준:
- `npx skills add` 한 줄로 설치되고 `npx skills remove` 한 줄로 제거된다.
- 제거 후 코어 동작이 변하지 않는다.
- 스킬 설치 시 코어 재시작이 필요하지 않다.
- 스킬 파일에 실행 가능한 코드가 포함되지 않는다.

### FR-102: 전제 조건 확인과 우아한 포기 (L2)

요구사항:
- 녹화를 시작하기 전 `airec --version`으로 가용성을 확인한다. 실패하면 설치 안내를 **1회만** 하고, 사용자가 설치를 원하지 않으면 그 세션에서 다시 묻지 않는다.
- 비윈도우 환경에서는 airec 호출을 시도하지 않고 즉시 텍스트 보고로 전환한다.
- `send_media` 도구가 없으면(코어가 구버전) 녹화를 시작하지 않는다. 보낼 수 없는 파일을 만들지 않는다.
- 어떤 전제 조건 실패도 원래 작업(사용자가 시킨 GUI 작업)을 중단시키지 않는다.

수용 기준:
- airec 미설치 상태에서 GUI 작업 지시 시, 작업은 정상 수행되고 보고는 텍스트로 이뤄진다.
- 설치 안내가 한 세션에서 두 번 이상 반복되지 않는다.
- 비윈도우에서 airec 관련 명령이 한 번도 실행되지 않는다.

### FR-103: 녹화 판단 규칙 (L2)

요구사항 — 스킬은 다음을 지시한다.

- **시작**: 컴퓨터 조작(설치 마법사, 브라우저 폼, 데스크톱 앱 설정, UI 자동화)을 시작하기 직전에 녹화를 건다. 코드 편집·빌드·테스트·파일 조작처럼 화면에 의미가 없는 작업은 녹화하지 않는다.
- **대상**: 전체 모니터보다 대상 창을 우선한다. 창을 특정할 수 없을 때만 모니터를 쓴다. `AMBIGUOUS_TARGET`이 오면 후보 목록으로 질의를 좁히고, 추측하지 않는다.
- **상한**: 항상 `--max-duration`을 부여한다(기본 30분). 세션이 방치돼도 반드시 끝나게 한다.
- **종료**: 작업이 끝나면 즉시 종료하고 전송한다. 사용자가 묻기 전에 보낸다.
- **중복 방지**: 활성 세션이 있으면 새로 시작하지 않는다(`airec status --json`으로 확인).
- **저장 위치**: 프로젝트 디렉터리를 오염시키지 않는다. 임시 디렉터리 또는 `%LOCALAPPDATA%\dm-plz\recordings\` 아래에 둔다.

수용 기준:
- "설치 마법사 진행해줘"에서 별도 요청 없이 녹화가 시작되고 종료 후 전송된다.
- "이 함수 리팩터링해줘"에서 녹화가 시작되지 않는다.
- 녹화 파일이 사용자의 git 작업 디렉터리에 생성되지 않는다.
- 연속 두 개의 GUI 작업에서 세션이 중복 생성되지 않는다.

### FR-104: 증거 신뢰도 판정 (L2)

요구사항 — 스킬은 `stop_reason`을 다음 표대로 해석하고, 결과를 캡션과 사용자 보고에 모두 반영한다.

| `stop_reason` | 신뢰 | 캡션 문구 |
| --- | --- | --- |
| `requested` | ✅ | 정상 종료 |
| `duration_limit` | ✅ | 지정 시간 도달로 종료 |
| `max_duration` | ✅ | 상한 시간 도달 — 작업 전체를 담지 않았을 수 있음 |
| `target_lost` | ⚠️ | 대상 창이 사라져 중단됨 |
| `error` | ⚠️ | 녹화 파이프라인 오류로 중단됨 |
| `aborted_on_failure` | ⚠️ | 다른 대상 실패로 함께 중단됨 |
| 그 외/누락 | ⚠️ | 종료 사유 불명 |

- `saved` 이벤트를 받지 못했거나 파일 크기가 0이면 전송하지 않고 텍스트로만 보고한다.
- 신뢰할 수 없는 녹화도 전송은 하되, **성공으로 단정하지 않는다.** 사용자에게 그대로 전달한다.
- **캡션은 사용자가 쓰는 언어로 작성한다.** 위 표의 문구는 의미이지 복사할 문자열이 아니다. 사용자에게 도달하는 모든 줄(캡션, 용량 실패 안내, 프라이버시 고지)에 동일하게 적용하며, 숫자·파일 경로·✅/⚠️ 마커는 그대로 둔다.

수용 기준:
- 녹화 중 대상 창을 강제로 닫으면 캡션 첫 줄에 ⚠️ 경고가 붙는다.
- 알 수 없는 `stop_reason`에서도 처리가 중단되지 않는다.
- 모델이 `trusted: false`인 결과를 "작업 성공"의 근거로 사용하지 않는다.
- 한국어로 대화한 사용자는 한국어 캡션을, 영어로 대화한 사용자는 영어 캡션을 받는다.

### FR-105: 용량 초과 대응 규칙 (L2)

요구사항 — `MEDIA_TOO_LARGE`를 받으면 스킬은 다음 순서를 따른다.

1. `airec convert <mp4> --out <gif> --fps 10 --width 960 --json`
2. 여전히 초과하면 `--fps 6 --width 480`으로 1회 더
3. 그래도 안 되면 **포기하고** 로컬 절대 경로·크기·재생 시간을 텍스트로 안내

- 축소 시도는 최대 2회다. 무한 재시도하지 않는다.
- 변환 결과가 원본보다 크면 그 단계는 실패로 본다(스크롤·영상 콘텐츠에서 실제로 일어난다).
- 어떤 경우에도 원래 보고 메시지는 전송한다. 침묵하지 않는다.

수용 기준:
- 200 MB 입력이 최종적으로 텍스트 안내에 도달한다.
- 축소 시도가 3회 이상 발생하지 않는다.
- 첨부 실패가 작업 보고 누락으로 이어지지 않는다.

### FR-106: 프라이버시 규칙 (L2)

요구사항 — 스킬은 다음을 지시한다.

- 비밀번호 입력, 토큰 표시, 개인 메시지, 금융 정보가 화면에 있을 것으로 예상되면 녹화를 시작하지 않거나 대상 창을 좁힌다.
- 전체 모니터 녹화는 대상 창을 특정할 수 없을 때의 마지막 수단이다.

- 사용자가 명시적으로 "녹화하지 마"라고 하면 그 세션 동안 녹화하지 않는다.

수용 기준:
- 비밀번호 관리자 창이 열린 상태에서 전체 모니터 녹화를 시작하지 않는다.
- 첫 전송 메시지에 프라이버시 고지가 포함된다.
- 사용자의 녹화 중단 지시가 세션 내내 유지된다.

- 두 스킬 동시 설치 시 중복된 녹화 세션이 생기지 않는다.

## 9. 훅과 스킬/MCP의 역할 분담

DM-Plz의 현행 구조는 훅 중심이다. 세 훅이 각각 메신저 왕복을 수행한다. 이 설계는 모델이 "지금 사용자에게 물어봐야 한다"를 스스로 판단하지 못하던 시기의 합리적 선택이었다.

지금은 다르다. 모델은 작업 성격을 보고 증거가 필요한지, 지금이 보고할 시점인지 스스로 판단한다. 그렇다면 훅으로 강제 개입할 이유가 없다.

> 훅은 "모델이 스스로 진입할 수 없는 지점"에만 쓴다. 그 외는 스킬로 지시하고 MCP 도구로 실행한다.

**훅이 반드시 필요한 조건 (하나라도 해당하면 훅)**

1. **무한 대기가 필요하다.** MCP 도구 호출은 모델의 턴 안에서 끝나야 하므로, 수 시간 대기는 훅 timeout 예산 위에서만 성립한다.
2. **모델의 협조 없이 개입해야 한다.** 권한 요청은 런타임이 발생시키는 이벤트이지 모델이 호출하는 도구가 아니다.
3. **턴 종료 이후에 실행되어야 한다.** Stop 훅의 속행 지시(exit code 2)는 모델이 이미 멈춘 뒤 동작해야 한다.
4. **누락되면 사용자가 원격에서 복구할 수단이 없다.**

네 번째가 결정적이다. 모델 성능이 올라 대부분의 판단을 맡길 수 있게 됐더라도 **판단 실패의 비용이 경로마다 다르다.**

Claude가 질문을 MCP로 보내는 것을 잊고 터미널에만 출력하면, 세션은 응답을 기다리며 멈춘다. 사용자는 폰만 갖고 있으므로 **아무것도 할 수 없다.** 메시지가 안 왔으니 답할 대상이 없고, 세션은 스스로 풀리지 않으며, 복구하려면 PC 앞으로 가야 한다. DM-Plz를 쓰는 이유가 통째로 무너진다.

반면 증거 전송을 잊으면 사용자는 "아까 그거 보내줘"라고 하면 된다. 세션은 살아 있고 복구 비용은 메시지 한 줄이다.

> 판단을 모델에게 넘길지 결정하는 기준은 "모델이 잘하는가"가 아니라 **"모델이 틀렸을 때 사용자가 원격에서 복구할 수 있는가"**다.

**스킬 + MCP로 충분한 조건 (모두 만족)**

- 모델이 "지금 하는 게 맞다"를 문맥으로 판단할 수 있다.
- 실행이 모델의 턴 안에서 완결된다.
- 모델이 누락해도 세션이 멈추지 않고, 사용자가 메신저에서 한 마디로 복구할 수 있다.

적용 결과:

| 기능 | 방식 | 모델이 누락하면 |
| --- | --- | --- |
| 녹화 시작·종료·전송 | 스킬 + MCP | "보내줘" 한 마디로 복구 |
| 임의 파일 첨부 | MCP (`send_media`) | 사용자가 직접 요청 가능 |
| 진행 보고 | 스킬 + MCP (기존 도구) | Stop 훅이 어차피 요약을 보냄 |
| 질문·답변 대기 | **훅 유지** | **세션이 멈추고 원격 복구 불가** |
| 권한 승인 대기 | **훅 유지** | **세션이 멈추고 원격 복구 불가** |
| 종료 후 속행 지시 | **훅 유지** | **다음 지시를 넣을 창구가 사라짐** |

굵은 세 줄이 훅이 존재해야 하는 전부다. 이 기능은 **신규 훅을 하나도 추가하지 않으며**, v0.1에서는 기존 훅 핸들러 코드도 건드리지 않는다. 부수 효과로 훅 300초 예산 리스크가 설계 단계에서 사라진다.

#### 미해결 문제

- **문제**: 장기적으로 `Stop` 훅의 "보고" 부분을 스킬로 대체할 수 있는지
- **영향**: 대체 가능하면 Stop 훅 충돌 문제(다른 플러그인과의 경합)와 `continueInstruction` 버그 우회가 사라진다. 다만 "다음 지시 무한 대기"는 훅 없이 성립하지 않으므로 완전 대체는 불가
- **후보**: 훅 유지 / 보고는 스킬, 대기만 훅으로 축소
- **결정 필요 시점**: v0.2 설계 전

## 10. 기술 아키텍처

```txt
┌─ L2: dm-plz-evidence 스킬 (선택 설치, 코드 없음) ──────────┐
│  언제 녹화할지 · 대상 선택 · stop_reason 판정              │
│  용량 폴백 규칙 · 프라이버시 규칙 · 캡션 조립              │
└───────┬────────────────────────────────┬───────────────────┘
        │ Bash/PowerShell                │ MCP
        ▼                                ▼
┌─ L3: airec.exe (선택 설치) ─┐  ┌─ L1: DM-Plz 코어 ────────┐
│  start / status / stop      │  │  send_media 도구         │
│  convert                    │  │  MessagingProvider       │
│  JSONL + stop_reason        │  │    .sendMedia()          │
└───────┬─────────────────────┘  └───────┬──────────────────┘
        │                                │ HTTPS multipart
        ▼                                ▼
   MP4 / GIF 파일  ──── file_path ──► Telegram / Discord API
```

세 레이어는 서로를 직접 import하지 않는다. L2는 문서이고, L1과 L3를 각각 도구 호출로만 사용한다. L1은 L3의 존재를 모른다.

#### 게이트 수정 (v0.5)

초안은 "신규 파일 0개, 250줄 이내"를 릴리즈 게이트로 잡았다. 구현 결과 이 기준은 **잘못된 대리 지표**였다.

### 10.3 airec 호출 계약 (L2가 사용)

스킬은 airec의 stdout JSONL만 신뢰하고 stderr는 진단용으로 취급한다. 사용하는 이벤트는 다음으로 한정한다.

```jsonc
{"event":"started","session":"a1b2"}
{"event":"saved","session":"a1b2","file":"...","stop_reason":"requested","duration_ms":12400,"frames":372}
{"event":"error","code":"TARGET_NOT_FOUND","message":"...","data":{"candidates":[]}}
```

알 수 없는 `event`와 필드는 무시한다. airec가 이벤트를 추가해도 규칙이 깨지지 않게 하기 위한 원칙이다. 이 계약은 **문서상의 규칙이지 파서 코드가 아니다** — JSONL 해석은 모델이 한다.

### 10.4 업로드 메모리 특성

초안은 "파일 크기와 무관하게 프로세스 메모리 +50 MB 이내"를 요구했다. 구현과 독립 검증 결과 이 목표는 현재 런타임에서 달성 불가능하며, 달성하려는 시도가 더 큰 비용을 만든다.

**측정값** (`fetch` + `FormData` + `BunFile`, Bun 1.3.9)

| 업로드 | JS 힙 | 프로세스 RSS |
| --- | --- | --- |
| 5 MiB (HTTP) | +0.0 MB | +10.4 MB |
| 50 MiB (HTTP) | +0.0 MB | +100.2 MB |
| 5 MiB (HTTPS) | +0.0 MB | +9.8 MB |
| 50 MiB (HTTPS) | +0.0 MB | +100.1 MB |

힙은 늘지 않지만 네이티브 쪽에서 파일 크기의 약 2배가 잡힌다. 힙만 보면 "스트리밍된다"는 잘못된 결론에 이른다.

**검토한 대안**

| 방식 | 메모리 | 탈락 사유 |
| --- | --- | --- |
| 수동 `ReadableStream` body | 낮음 | `fetch`가 스트림 body에서 수동 `Content-Length`를 제거해 chunked 전송이 된다. 그 상태로 abort하면 Bun 1.3.9가 프로세스째 패닉한다 — 타임아웃이 MCP 서버를 죽인다 |
| raw `node:net`/`node:tls` HTTP | 낮음 | 리다이렉트·프록시·chunked 디코딩·keep-alive를 영구히 자체 부담. 1차 구현이 이 경로였고 타입 파일까지 오염시켰다 |
| 기본 상한 축소(20 MB 등) | 중간 | Telegram이 받을 수 있는 파일을 스스로 거부하게 된다 |

**결정: `fetch` + `FormData`를 유지하고 기준을 실측에 맞춘다.**

- 스파이크는 유계다. 상한이 Telegram 50 MB / Discord 10 MiB이므로 최악 ~100 MB이며 업로드 종료와 함께 해제된다.
- 실제 증거 파일은 훨씬 작다. 측정에 쓴 airec 녹화본이 0.4~3.6 MB이고, 이 구간의 스파이크는 10 MB 미만이다. 50 MB는 예외 경로다.
- HTTP 클라이언트를 자체 유지하는 비용이 100 MB 스파이크보다 비싸다. 독립 검증에서 `fetch` 구현은 타임아웃·정리·재시도를 모두 통과했다.

**대체 기준**: 업로드 중 RSS 증가가 파일 크기의 3배를 넘지 않고, 업로드 종료 후 해제된다.

재검토 조건: Bun이 스트림 body의 `Content-Length`를 지원하거나 abort 패닉이 고쳐지면 수동 스트림 방식을 다시 잰다.

## 12. 에러 모델 (L1)

```ts
type DmplzMediaError = {
  code: string
  message: string
  data?: {
    sizeBytes?: number
    limitBytes?: number
    path?: string
  }
}
```

| 코드 | 의미 | 스킬의 대응(L2) |
| --- | --- | --- |
| `MEDIA_DISABLED` | `DMPLZ_MEDIA_ENABLED=false` | 텍스트 보고로 전환 |
| `FILE_NOT_FOUND` | 경로 없음 | 녹화 결과 재확인, 실패 시 텍스트 보고 |
| `FILE_EMPTY` | 크기 0 | 증거로 취급하지 않음 |
| `PATH_NOT_ABSOLUTE` | 상대 경로 | 절대 경로로 재호출 |
| `MEDIA_TOO_LARGE` | 상한 초과 (`limitBytes` 포함) | FR-105 폴백 진입 |
| `MEDIA_SEND_FAILED` | 업로드 실패 | 1회 재시도 후 로컬 경로 안내 |
| `MEDIA_TIMEOUT` | 업로드 타임아웃 | 동일 |

airec 쪽 에러 코드(`TARGET_NOT_FOUND`, `AMBIGUOUS_TARGET` 등)는 **코어가 알지 못한다.** 스킬이 airec 출력을 직접 읽고 판단한다.

원칙: 코어는 에러를 정확히 보고할 뿐 복구를 시도하지 않는다. 복구 판단은 L2에 있다.

## 13. 보안·프라이버시 정책

화면 녹화는 DM-Plz가 지금까지 다루던 어떤 데이터보다 민감하다. 텍스트는 Claude가 무엇을 쓸지 통제할 수 있지만 화면은 통제할 수 없다.

다만 위협을 정확히 잡아야 한다. 과장된 위협에 대응하면 쓸모없는 제약만 남고, 진짜 위험은 그대로 남는다.

### 13.1 위협 모델: 목적지가 전부다

`send_media`가 임의 경로의 로컬 파일을 전송할 수 있다는 사실 자체는 새로운 위협이 아니다.

- **목적지가 고정돼 있다.** 파일은 `DMPLZ_TELEGRAM_CHAT_ID` / `DMPLZ_DISCORD_CHANNEL_ID`가 가리키는 곳, 즉 사용자 본인의 채팅으로만 간다. 프롬프트 인젝션으로 `.env`를 지목당하는 최악의 경우에도 결과는 "내 텔레그램에 내 `.env`가 올라온다"이다. 외부로 나가는 경로가 아니다.
- **이미 가능한 일이다.** 모델은 지금도 `Read`로 파일을 읽어 `send_message`에 그대로 붙여 보낼 수 있다. `send_media`는 새 문을 여는 것이 아니라 기존 문의 편의 버전이다. 여기에만 확장자 allowlist를 거는 것은 앞문을 열어둔 채 뒷문에 자물쇠를 다는 격이다.
- **목적지 설정을 바꿀 수 있는 공격자는 이미 이겼다.** `~/.claude/settings.json`을 쓸 수 있다는 것은 임의 명령 실행 권한이 있다는 뜻이고, 그 시점에 DM-Plz의 어떤 제약도 의미가 없다.

따라서 **유일하게 실질적인 보안 요구사항은 "목적지를 모델이 고를 수 없게 하는 것"이다.**

- 도구 입력 스키마에 chat/channel ID 필드를 두지 않는다.
- `sendMedia()`의 `route`는 기존 라우팅 규칙 중 하나를 고르는 열거형이며, 실제 ID는 provider가 환경변수에서 읽는다.
- 이 규칙은 기존 텍스트 도구(`send_message` 등)에도 동일하게 유지한다.

### 13.2 확장자 allowlist를 두지 않는 이유

- 위 근거에 따라 방어 효과가 사실상 없다(`Read` + `send_message` 경로가 그대로 열려 있다).
- 증거 파일 확장자를 예측하기 어렵다. 로그(`.jsonl`), 이벤트 타임라인, 리포트(`.html`), 크래시 덤프까지 사용자가 보내고 싶어할 수 있다.
- allowlist는 정상 사용을 막는 순간 사용자가 우회 방법을 찾게 만든다. 우회 경로는 더 통제하기 어렵다.

대신 **관측 가능성**으로 대응한다. 모든 전송의 파일 경로·크기·목적지 종류를 로그에 남겨 "무엇이 나갔는지"를 사후에 확인할 수 있게 한다.

### 13.3 실제로 남는 위험

목적지를 고정해도 사라지지 않는 것들이며, 이쪽이 진짜 대응 대상이다.

| 위험 | 설명 | 대응 |
| --- | --- | --- |
| **제3자 서버에 사본 생성** | Telegram/Discord는 E2E가 아니다. 전송한 파일은 그들 서버에 남고, 로컬에서 지워도 지워지지 않는다 | 문서 경고. 시크릿이 찍힌 녹화는 전송하지 않도록 스킬 규칙에 명시(FR-106) |
| **공유 채널 노출** | `DMPLZ_DISCORD_CHANNEL_ID`가 팀 채널이면 "본인에게만"이 성립하지 않는다. **이것이 가장 현실적인 유출 경로다** | 첫 전송 시 목적지 종류(개인 DM / 채널)를 고지. 채널 설정 시 README에서 개인 DM 사용을 권장 |
| **봇 토큰 유출 시 이력 열람** | 토큰이 새면 공격자가 채널 히스토리와 첨부를 읽을 수 있다 | 기존 위험이며 이 기능이 증폭시키는 정도만 문서화. 민감 파일 전송을 줄이는 것이 유일한 완화 |
| **첨부 URL 접근성** | Discord 첨부는 URL을 아는 사람이 접근할 수 있다(서명·만료 정책 변동) | 동일. 문서 경고 |
| **화면에 찍힌 시크릿** | 녹화 대상 창에 토큰·비밀번호가 보였을 수 있다 | L2의 프라이버시 규칙(FR-106). 대상 창 좁히기, 민감 화면 예상 시 녹화 안 함 |

핵심은 하나로 요약된다. **위험은 "파일이 내 손을 떠난다"는 사실 자체이지, "어떤 파일을 고를 수 있는가"가 아니다.**

### 13.4 레이어별 책임

**L1(코어)의 책임**
- 목적지를 모델이 지정할 수 없게 한다(§13.1). **이것이 코어의 유일한 보안 요구사항이다.**
- 로그에는 파일 경로·크기·목적지 종류·전송 결과를 남긴다.
- 새 전송 대상을 만들지 않는다. 기존 라우팅 규칙을 승계한다.
- 파일 내용에 대한 판단을 하지 않는다(§13.2).

**L2(모듈)의 책임**
- 민감 화면 예상 시 녹화하지 않거나 대상을 좁힌다(FR-106).
- 첫 전송 시 프라이버시 고지 1회.
- 전체 모니터보다 대상 창을 기본 권장.
- 자동 마스킹을 하지 않으며, 하지 않는다는 사실을 사용자에게 알린다. 오탐이 곧 유출이기 때문이다.

**설치가 곧 동의다.** 이 기능은 사용자가 명령 두 줄을 직접 실행해야 켜진다. 그 행위 자체가 opt-in이므로, 코어에 별도의 "녹화 활성화" 스위치를 두지 않는다. v0.2안의 `DMPLZ_RECORDING_ENABLED`는 이 판단에 따라 삭제됐다.

#### 미해결 문제

- **문제**: 전송 전 사용자 승인(`requestPermission` 재사용)을 스킬 규칙으로 넣을지
- **영향**: 넣으면 안전하지만 자동화 가치가 반감된다(폰을 봐야 함). 안 넣으면 실수로 민감 화면이 나갈 수 있다
- **후보**: 기본 없음 + 사용자가 원하면 지시로 켬 / 첫 N회만 승인 요구 / 항상 승인
- **결정 필요 시점**: v0.1 릴리즈 전

## 17. 주요 리스크

### 17.1 모듈 경계가 무너짐

문제:
- "이건 코어에 있는 게 편한데"가 반복되면 결국 v0.2안으로 되돌아간다.

대응:
- §3.3의 판정 질문("airec를 모르는 사용자에게도 쓸모 있는가")을 코드 리뷰 기준으로 사용한다.
- 코어 diff 250줄, 신규 파일 0개를 릴리즈 게이트로 삼는다(§15).
- 코어에 `airec`라는 문자열이 등장하면 리뷰에서 막는다(도구 설명의 안내 문장 1곳 제외).

### 17.2 목적지가 개인 채널이 아닌 경우

문제:
- `DMPLZ_DISCORD_CHANNEL_ID`가 팀 채널을 가리키면 "본인에게만 간다"는 전제가 깨진다. 화면에 찍힌 토큰이 팀 전체에 공개된다. §13.3에서 가장 현실적인 유출 경로로 분류된 항목이다.

대응:
- 첫 전송 메시지에 목적지 종류(개인 DM / 공유 채널)를 명시한다. 사용자가 자기 설정을 자각하게 만든다.
- README에서 증거 녹화 사용 시 개인 DM 설정을 권장한다.
- 스킬 규칙(FR-106)에서 민감 화면 예상 시 녹화하지 않도록 지시한다 — 목적지와 무관하게 유효한 방어다.

### 17.3 제3자 서버에 시크릿 사본이 남음

문제:
- Telegram/Discord는 E2E가 아니다. 한 번 전송한 파일은 로컬에서 지워도 그들 서버에 남는다. 녹화본은 사용자가 내용을 완전히 통제할 수 없는 데이터다.

대응:
- 전송 전에 막는 것이 유일한 실효 방어이며, 이는 L2의 프라이버시 규칙에 달려 있다(FR-106).
- 대상 창 좁히기를 기본 권장으로 문서화한다. 전체 모니터 녹화는 다른 창의 내용까지 증거에 섞는다.
- 자동 마스킹은 하지 않으며, 하지 않는다는 사실을 사용자에게 알린다. 오탐이 곧 유출이다.

**하지 않는 대응:** 확장자·경로 allowlist. 근거는 §13.2 — `Read` + `send_message` 경로가 그대로 열려 있어 방어 효과가 없고 정상 사용만 막는다.

### 17.4 모델이 도구 호출을 누락

문제:
- 스킬 기반이라 모델이 녹화 시작을 잊으면 증거가 남지 않고, 작업 후에는 되돌릴 수 없다.

대응:
- 세션을 멈추는 실패가 아니므로 허용 가능하다(§9). 사용자가 "다시 하면서 녹화해줘"로 복구한다.
- 스킬 `description`에 트리거 조건을 구체적으로 써서 로드 정확도를 높인다.
- v0.2의 Stop 훅 안전망은 "시작했는데 전송을 잊은" 경우만 구제한다. 시작 자체를 잊은 경우는 구제하지 않는다.
- 사용자가 "녹화하면서 진행해줘"로 강제할 수 있음을 문서에 명시한다.

### 17.5 파일 크기 예측 실패

문제:
- 스크롤·영상이 포함된 화면은 GIF 변환 시 원본보다 커진다(airec README가 명시).

대응:
- 변환 결과가 원본보다 크면 실패로 처리(FR-105).
- `--max-duration` 기본 30분을 항상 부여(FR-103).
- 축소 시도 2회 상한.

### 17.6 airec 계약 변경

문제:
- airec가 JSONL 필드나 종료 코드를 바꾸면 스킬 규칙이 어긋난다.

대응:
- 알 수 없는 이벤트·필드는 무시(§10.3).
- 규칙이 문서이므로 수정에 릴리즈가 필요 없다. 스킬만 갱신하면 된다. **이것이 모듈 구조의 실질적 이득 중 하나다.**

### 17.7 두 스킬의 중복

문제:
- `airec` 스킬과 `dm-plz-evidence`가 동시에 로드되면 지시가 겹치거나 충돌할 수 있다.

대응:
- 역할을 명시적으로 분리하고 상호 참조한다(FR-107).
- 충돌 시 안전한 쪽(녹화하지 않음, 전송하지 않음)을 따르도록 규정한다.

## 20. 상세 수용 기준 (v0.1 릴리즈 체크리스트)

**모듈성 (최우선)**
- [ ] §11 조합 8종 전부에서 정의된 동작이 확인된다
- [ ] 코어에 녹화·세션·폴백·보존 코드가 0줄이다
- [ ] 코어의 신규 코드가 airec 없이도 쓸모 있다(스크린샷·로그 첨부)
- [ ] 코어 코드에 `airec` 문자열이 도구 설명 1곳 외에 등장하지 않는다
- [ ] 스킬 제거 후 코어 동작이 변하지 않는다
- [ ] 스킬 설치·제거에 코어 재시작이 필요 없다

**L1 코어**
- [ ] Telegram에서 12초 MP4가 인라인 재생된다
- [ ] Telegram에서 60초 MP4가 `sendVideo`로 전송된다
- [ ] Discord 채널과 DM 양쪽에서 MP4 첨부가 표시된다
- [ ] 상한 초과 시 업로드 요청 없이 `MEDIA_TOO_LARGE`와 `limitBytes`가 반환된다
- [ ] 50 MB 업로드에서 RSS 증가가 파일 크기의 3배 이내이고 종료 후 해제된다(§10.4)
- [ ] 검사 통과 후 커진 파일이 검사 시점 크기만큼만 전송된다
- [ ] 강제 종료된 녹화(`mvhd` duration 0)가 `sendVideo`로 라우팅된다
- [ ] 존재하지 않는 경로·상대 경로·빈 파일이 각각 구조화 에러로 반환된다
- [ ] 미디어 전송 중 MCP 도구 목록 조회가 정상 동작한다
- [ ] 훅 코드가 변경되지 않았다(`env` 블록 제외)
- [ ] **도구 입력 스키마에 chat/channel ID 필드가 없다**
- [ ] 임의 목적지로 전송을 시도할 방법이 도구 표면에 존재하지 않는다
- [ ] 전송 로그에 경로·크기·목적지 종류가 남는다

- [ ] 200 MB 결과가 축소 2회 후 텍스트 안내에 도달한다

## 22. 최종 요약

DM-Plz는 이미 원격 조종 루프를 갖고 있고, airec는 이미 신뢰할 수 있는 증거 파일을 만든다. 남은 것은 그 사이를 잇는 일인데, **어디에 코드를 놓느냐가 무엇을 만드느냐보다 중요하다.**

이 PRD의 답은 "가능한 한 적게, 가능한 한 바깥에"다. 코어에는 파일 하나를 첨부해 보내는 능력만 넣는다 — airec를 모르는 사용자도 스크린샷과 로그를 보내는 데 쓸 것이기 때문이다. 언제 녹화하고 어떻게 판정하고 용량이 넘치면 무엇을 할지는 전부 스킬 문서로 나가고, 그 스킬은 사용자가 원할 때 한 줄로 설치하고 한 줄로 지운다.

결과적으로 v0.1은 **코어 250줄 미만, 신규 파일 0개, 스킬 문서 1개**다. 서버 모듈 6개와 MCP 도구 2개가 사라졌고, 그 자리는 모델의 판단이 채운다.

훅을 늘리지 않는 것도 같은 이유다. 증거 전송을 모델이 잊으면 사용자는 폰에서 한 마디로 복구한다. 질문 전달을 잊으면 폰에서 할 수 있는 게 없다. 그래서 질문·권한·속행만 훅으로 남고 나머지는 전부 모델에게 간다.

이 기능의 최우선 요구사항은 "잘 동작한다"가 아니다. **"없어도 아무도 아쉽지 않고, 있어도 아무것도 무거워지지 않는다"**이다.
